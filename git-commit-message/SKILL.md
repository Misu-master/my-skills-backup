# Git Commit Message 生成器

根据用户提供的文件路径和代码变更，生成符合 Conventional Commits 规范的中文提交备注。

## 触发场景

- 用户说"写git备注"、"git commit message"、"提交备注"、"commit message"
- 用户提供文件路径或代码片段，需要生成提交说明
- 用户完成代码修改后需要规范的提交信息

## 提交粒度：按功能单元拆分

**核心原则：一次提交只对应一件事。同一功能逻辑的修改合并为一次提交，不同功能拆分提交。**

禁止的操作：

- ❌ `git add <项目目录>/` 一次性把整个项目打包提交
- ❌ 把项目脚手架、客户端封装、业务逻辑、配置模板混在同一个 commit 里

正确的做法：

- ✅ 先 `git status --untracked-files=all` 列出全部改动，按功能域分组
- ✅ 每组只用精确文件路径 `git add`，逐个文件指定，不使用目录通配
- ✅ 每组提交前 `git diff --cached` 自查，确认只包含同一件事
- ✅ 一组一个 commit，全部完成后再统一 `git push`

### 合并与拆分的判断标准

**合并为一个提交**（同一功能意图的必要组成）：

- 新增函数 + 调用方改为使用该函数 + 该函数需要的新配置项
- 修复缺陷 + 补充该缺陷的回归测试
- 重命名模块 + 更新所有引用位置

**拆分为多个提交**（可独立描述、独立回滚）：

- 新增基础设施（数据库客户端、缓存客户端、通知客户端）→ 各自独立提交
- 项目脚手架与依赖声明 → 独立提交（chore）
- 纯业务逻辑实现 → 独立提交
- 无关的格式化、注释调整 → 独立提交（style / docs）

**拆得过碎同样有害**：给某个函数加一行注释、修正一个错别字不应单独提交。判断标准是：**一个提交 = 一个能被独立描述、独立回滚的完整功能意图**。

### 示例：多模块项目首次提交的拆分顺序

| 顺序 | 提交 | 文件 |
|------|------|------|
| 1 | `chore(脚手架): 新增项目脚手架与依赖` | 依赖声明、版本文件、忽略规则、包初始化文件 |
| 2 | `feat(pgsql_client): 新增 PG 同步异步单例连接池` | 数据库客户端 |
| 3 | `feat(redis_client): 新增 Redis 客户端封装` | 缓存客户端 |
| 4 | `feat(dingtalk_client): 新增钉钉消息通知客户端` | 通知客户端 |
| 5 | `feat(ziniao_client): 新增紫鸟客户端封装` | 第三方客户端封装 |
| 6 | `feat(pre_logic): 新增三源关联与账号店铺映射` | 业务前置逻辑 + 其依赖的配置 |
| 7 | `feat(main): 接入账号店铺映射主流程` | 主流程调用方 |

顺序必须保证依赖关系：后面的提交依赖前面的提交，每个提交自身是自洽可解释的。

## 输出格式

### 单个文件
```
<类型>(<作用域>): <简短描述>

<详细说明>
```

### 多个文件

先按功能域分组，再决定输出形态：

- **同一功能**的多个文件 → 合并为一个提交备注，正文用列表列出各文件的改动点
- **不同功能**的文件 → 各自独立提交，分别标注文件名

**示例：同一功能的多个文件**

```
feat(pre_logic): 新增店铺与紫鸟账号的映射整理函数

- pre_logic.py: 新增 build_run_user_infos, 按店铺清单、数据库映射、
  账号密码三源关联生成待运行账号列表
- config.py: 补充紫鸟客户端路径配置项
- main.py: 主流程改为调用该函数, 移除内联的归组逻辑
```

**示例：不同功能的文件**

**config.py**
```
feat(config): 新增应用配置模块，支持多数据库和飞书配置

使用 pydantic-settings 从 .env 读取配置，支持 MySQL/MSSQL/Redis/飞书
的配置解析，包含空值自动转换为 None 的验证逻辑。
```

**database.py**
```
feat(database): 新增 SQLite 异步引擎和会话管理

创建异步数据库引擎、SessionFactory、依赖注入函数 get_db()，
以及自动创建数据库目录和表的工具函数。
```

## 提交类型

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | feat(api): 新增用户认证接口 |
| `fix` | 修复 bug | fix(auth): 修复 JWT token 过期问题 |
| `refactor` | 重构（非功能/非修复） | refactor(db): 优化数据库连接池管理 |
| `docs` | 文档变更 | docs(readme): 补充安装说明 |
| `style` | 代码格式（不影响功能） | style(lint): 统一缩进和引号风格 |
| `test` | 新增或修改测试 | test(auth): 补充登录失败用例 |
| `chore` | 构建/工具/依赖变更 | chore(deps): 升级 pydantic 到 2.0 |
| `perf` | 性能优化 | perf(query): 使用索引优化查询速度 |
| `ci` | CI/CD 配置变更 | ci(github): 添加自动化测试 workflow |

## 作用域规则

**一般规则：使用具体文件名（不含扩展名）作为作用域**

| ✅ 正确 | ❌ 错误 |
|---------|---------|
| feat(base_model) | feat(core) |
| fix(config) | fix(settings) |
| refactor(database) | refactor(db) |
| feat(resources) | feat(manager) |

**例外：`__init__.py` 文件使用模块名**

对于包初始化文件 `__init__.py`，使用其所在目录的模块名作为作用域：

| 文件路径 | ✅ 作用域 | ❌ 作用域 |
|----------|----------|----------|
| `src/core/__init__.py` | core | __init__ |
| `src/integrations/__init__.py` | integrations | __init__ |
| `src/middlewares/__init__.py` | middlewares | __init__ |

**示例**：
```
feat(core): 新增核心模块包初始化文件

定义核心基础设施模块的包标识，包含配置、数据库、异常处理、资源管理等全局基础组件。
```

## 备注内容规范

### 首行（必填）
- 格式：`<类型>(<作用域>): <描述>`
- 长度：不超过 50 个字符
- 语言：中文
- 时态：使用现在时，如"新增"、"修复"、"优化"

### 正文（可选但推荐）
- 与首行空一行
- 详细说明变更内容、原因、影响范围
- 每行不超过 72 个字符
- 使用列表形式更清晰

## 工作流程

1. **接收输入**：用户提供的文件路径和/或代码变更
2. **列出改动**：执行 `git status --untracked-files=all` 获取完整改动清单
3. **按功能分组**：把改动拆成若干可独立描述的组，同一功能的文件归为一组
4. **逐组提交**：每组用精确文件路径 `git add`，`git diff --cached` 自查后单独 commit
5. **分析上下文**：读取文件内容，理解变更意图
6. **判断类型**：根据变更性质选择正确的提交类型
7. **确定作用域**：同一功能多文件时取主文件名为作用域，单文件时用该文件名
8. **生成备注**：首行简洁，正文详细
9. **输出结果**：按功能组输出备注，并说明各组包含哪些文件
10. **最后推送**：所有组提交完毕后再执行 `git push`

## 注意事项

- 始终使用中文
- 作用域必须是具体文件名
- 首行不超过 50 字符
- 正文每行不超过 72 字符
- 禁止用 `git add <目录>/` 打包提交整个项目
- 同一功能的多个文件合并为一个提交，不同功能必须拆分
- 每个提交都必须能被独立描述和独立回滚
- 如果用户没有提供足够信息，可以询问更多上下文
